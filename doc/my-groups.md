# Own mail groups

The reference of `MyGroupsService` (#251, #252). The README keeps its overview, with a short example: [`MyGroupsService`](../README.md#mygroupsservice).

## `MyGroupsService`

Every user keeps their own groups of people in Smartschool: "Mijn groepen" in the profile (`/?module=Profile&file=mygroups`, "Stel uw eigen favoriete groepen samen"). The compose form of Messages finds such a group by its name, as a group, so that a message to it goes to all its members: they are personal mail groups. The service reads them: the list of own groups and the members of one. It creates a group, changes its name and description, and deletes it (#252). It changes no members (#253).

### Methods

| Method | Returns | Description |
|---|---|---|
| `list()` | `Future<List<MyGroup>>` | The own groups, sorted by name as Smartschool lists them (`GET /?module=Profile&file=mygroups`); an empty list when the user has none. Each `MyGroup` has its `id` (the `mID` of its links), `name` and `description` (`""` when none). |
| `members(group)` | `Future<List<MyGroupMember>>` | The members of an own group, in the order of its members page (by name); an empty list for a group without members. It reads the group's members page (`GET ...&function=users&mID={id}`), and then, in that page's session, the member picker's selection of the group (see below), and checks that both list the same members. Each `MyGroupMember` has its `userId`, `name` (last name first), `ssId` (its platform), `schoolName` (`null` when empty) and `type` (`U`, a person). A group the user does not have (any more) is a `SmartschoolMyGroupNotFoundError`. |
| `findRecipient(group)` | `Future<MessageSearchGroup?>` | The group as a recipient of a message: the `MessageSearchGroup` that `MessagesService.searchRecipientsForCompose` finds for its name with the group's ID as its `groupId` and its name as its `displayName` (seen live, 2026-11-16), or `null`. Pass it to `SendMessageParams.toGroups` (or `ccGroups`, `bccGroups`). A group with a blank name is an `ArgumentError`, before anything is sent. |
| `create(name: ..., description: '')` | `Future<MyGroup>` | Makes an own group (#252) and returns it as the list shows it after the save: the group with the name and description sent that the list has after the save and did not have before (Smartschool's answer does not name its ID). Reads the list, loads the form for a new group for its token, and saves it once (see [Writes](#writes)). |
| `update(group, name: ..., description: ...)` | `Future<MyGroup>` | Changes the name, the description or both of an own group (#252), and returns it as the list shows it after the save. A `null` name or description keeps the one the group has, as its edit form has it (exactly: the list may not, see below); an empty description empties it. Reads the list (the group must be in it), loads the group's edit form for its token and values, and saves it once. |
| `delete(group)` | `Future<void>` | Deletes an own group (#252), with its member list. Reads the list (the group must be in it) and sends the delete once; it went through when Smartschool answers with the list without the group and the feedback "De actie werd correct uitgevoerd.". |

### What Smartschool answers

Seen live on 2026-11-16:

- **The list** is an HTML table with a row per group: its name, its description, and the links to edit it, to add people to it (`function=users&mID={id}`) and to delete it, which carry its ID. It does **not escape** a name or a description: a group named `a & "b"` is in the page as `a & "b"`, which the service reads as it is. A name that holds the text of an HTML entity (such as `&amp;`) is read as the character it names; only the group's edit form has such a name exactly. Smartschool strips tags when it saves a name or a description, so neither holds markup.
- **The members page** of a group has a row per member with the member's user ID and name, sorted by name, but not the member's platform (`ssId`), which a change of the members needs (#253). For an ID the user has no group of, Smartschool answers the list instead, with the feedback "De actie werd niet correct uitgevoerd!".
- **The member picker** ("Personen toevoegen" on the members page, Smartschool's general user picker) gives the platform. Loading the members page sets the picker's selection for the group (`usc` `mygroups_{id}`) in the PHP session to the current members, and the picker's dispatcher (`POST /?module=Userselect&file=dispatcher`, form-encoded `command`, the XML command format of the Messages dispatcher) answers the command `userSelect` / `get Items Selected` with that selection (`handle selected items`): each member as an `<item>` with its `type`, `id`, `ssId`, `name` and `schoolname`, or `<items />` for a group without members. The picker's own page did not need to be opened first. Without `X-Requested-With`, Smartschool answers the dispatcher with `302 Location: /?module=Homepage`; the service always sends it, and reports a redirect as a `SmartschoolMyGroupsError`.
- **The form** of a group (#252), `GET ...&function=addedit` for a new group and `...&function=addedit&mID={id}` for an existing one, is a `<form name="form" action="" method="post">` with a token (`_csrf_token`, a new one for every load), `store` (`1`) and the text inputs `name` and `desc`, filled in for an existing group (escaped in their `value`). It has no `mID` field: the ID is in the URL it posts to. For an ID the user has no group of, Smartschool answers the list with the feedback "De actie werd niet correct uitgevoerd!".
- **A save** (#252) posts the form, form-encoded, to the URL it was loaded from, with `_csrf_token`, `store`, `name` and `desc`, and is answered with `302 Location: /?module=Profile&file=mygroups&function=main` and an empty body, which does not name the group. Both fields go with every save. Text was saved as UTF-8 (`é` kept), with `&` and `"` as they are; tags are stripped (`gewijzigd <b>vet</b>` was saved as `gewijzigd vet`). The inputs have no `maxlength`; a limit of Smartschool was not tried.
- **A delete** (#252) is a GET, `...&function=delete&mID={id}`, which the web client sends behind a JavaScript `confirm()`. It is answered with `200` and the list itself (no redirect), without the group. A group with a member was deleted with its member list; the compose search of Messages no longer found it afterwards.
- **The outcome** of a write is only in a feedback message in the next page Smartschool renders, in a script: `var msg = "...", type = N`. A save that Smartschool refused (an empty name: nothing changed) has "De actie werd niet correct uitgevoerd!" (type `2`) in the list after the redirect; one that went through has no message. A delete that went through has "De actie werd correct uitgevoerd." (type `1`); a delete, or the edit form, of an ID that does not exist (any more) "De actie werd niet correct uitgevoerd!" (type `2`). Smartschool keeps the message in the session until a page shows it.

The picker's request carries state of the session of the members page, so it is not retried after logging in again, nor sent in another session than the page's: when Smartschool refuses its session, or the client logged in again since the page was loaded, `members` loads the page again (logging in first) and asks the picker once more, and throws a `SmartschoolSessionExpiredError` when that fails too.

A change of the members (the picker's steps, which replace the selection, #253) must not have a load of the group's members page between its steps on the same session. The calls of `members`, `create`, `update` and `delete` on one `SmartschoolClient` take turns, also those through another `MyGroupsService` of it; so a write's reads of the list before and after its save see no other write of the client in between. Clients that share one session (one cache folder) do not take turns, nor do the calls of `list`.

### Writes

`create`, `update` and `delete` (#252):

- **Checks before saving.** A blank name, or one that is empty once its tags are stripped, is an `ArgumentError`, before anything is sent: Smartschool refuses it without saying why. So is `update` without a name and a description. A name that another own group has already, as the list shows it, is an `ArgumentError` once the list was read (its message names that group by its ID): whether Smartschool allows two such groups was not tried, and they could not be told apart in the compose search. `update` and `delete` only change a group the list has: another is a `SmartschoolMyGroupNotFoundError`, before anything is saved or deleted.
- **Sent once.** A save is never sent again after logging in again (its token is in the session), nor in another session than its form's; when Smartschool refuses the session for it, it fails with a `SmartschoolSessionExpiredError`, and nothing was saved. The service sends a delete once too (like every GET, it goes out again after logging in when Smartschool refused the session for it, and did not handle it then).
- **Confirmed.** The service follows the redirect after a save at once, as Smartschool keeps the feedback in the session, and checks the list it shows: no feedback that the save was not done, and the new group (`create`) or the group (`update`) with the name and description sent, as the list shows them. A delete is confirmed by its answer: the list with the feedback type `1`, without the group; with the feedback type `2` and without the group, it was gone already (a `SmartschoolMyGroupNotFoundError`). Anything else is a `SmartschoolMyGroupSaveUnconfirmedError`: **list the groups before trying again**, since a create that went through and is sent again makes a second group (which `create` refuses by its name).
- **Plain text.** Name and description are saved as plain text: Smartschool strips tags. The writes return the group as the list shows it after the save, without them.

The models never print a name: `MyGroup.toString()` names a group by its ID, `MyGroupMember.toString()` a member by its type, ID and platform. The members of a group are mostly pupils.

Not covered: adding and removing members (#253), the length of a name and two groups with one name (not tried), and whether a pupil account has "Mijn groepen" (not tried).

### Errors

| Exception | Thrown when |
|---|---|
| `ArgumentError` | `create`, `update`: a blank name (or one that is empty without its tags), or a name that another own group has (once the list was read); `update` without a name and a description. Nothing was saved |
| `SmartschoolMyGroupsError` | Smartschool answered a read with something the service cannot use: another status than `200` (in `statusCode`; a redirect of the picker's request too), another page than the list, the members page or the form, a form without its token, a picker answer that is not `ok` or holds no selection, a row or item without its ID, or a members page and a picker selection that do not list the same members. Never an empty result; its message names a group by its ID only. From a write: a read before its save, so nothing was changed. Not a session problem |
| `SmartschoolMyGroupNotFoundError` | `members`, `update`, `delete`: the user has no own group with that ID (carries the `groupId`); for `update` and `delete`, nothing was saved or deleted. A `SmartschoolMyGroupsError` |
| `SmartschoolMyGroupSaveUnconfirmedError` | `create`, `update`, `delete`: the save or the delete went out, but Smartschool's answer does not confirm it (carries the `groupId`, `null` for a create; the `statusCode` of an answer with another status than expected; the `cause` when no usable answer came in). The change may or may not have been made: list the groups before trying again. Not a `SmartschoolMyGroupsError` |

The picker answering with an HTML page is a `SmartschoolUnexpectedPageError`, another answer that is not XML a `SmartschoolParsingError`, as for every XML command. A session Smartschool does not accept, also after logging in again, is a `SmartschoolSessionExpiredError`; no connection a `SmartschoolConnectionError`.
