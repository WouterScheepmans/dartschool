# Own mail groups

The reference of `MyGroupsService` (#251, #252, #253). The README keeps its overview, with a short example: [`MyGroupsService`](../README.md#mygroupsservice).

## `MyGroupsService`

Every user keeps their own groups of people in Smartschool: "Mijn groepen" in the profile (`/?module=Profile&file=mygroups`, "Stel uw eigen favoriete groepen samen"). The compose form of Messages finds such a group by its name, as a group, so that a message to it goes to all its members: they are personal mail groups. The service reads them: the list of own groups and the members of one. It creates a group, changes its name and description, and deletes it (#252). It adds people to a group, removes one, sets its members and empties it (#253).

### Methods

| Method | Returns | Description |
|---|---|---|
| `list()` | `Future<List<MyGroup>>` | The own groups, sorted by name as Smartschool lists them (`GET /?module=Profile&file=mygroups`); an empty list when the user has none. Each `MyGroup` has its `id` (the `mID` of its links), `name` and `description` (`""` when none). |
| `members(group)` | `Future<List<MyGroupMember>>` | The members of an own group, in the order of its members page (by name); an empty list for a group without members. It reads the group's members page (`GET ...&function=users&mID={id}`), and then, in that page's session, the member picker's selection of the group (see below), and checks that both list the same members. Each `MyGroupMember` has its `userId`, `name` (last name first), `ssId` (its platform), `schoolName` (`null` when empty) and `type` (`U`, a person). A group the user does not have (any more) is a `SmartschoolMyGroupNotFoundError`. |
| `findRecipient(group)` | `Future<MessageSearchGroup?>` | The group as a recipient of a message: the `MessageSearchGroup` that `MessagesService.searchRecipientsForCompose` finds for its name with the group's ID as its `groupId` and its name as its `displayName` (seen live, 2026-11-16), or `null`. Pass it to `SendMessageParams.toGroups` (or `ccGroups`, `bccGroups`). A group with a blank name is an `ArgumentError`, before anything is sent. |
| `create(name: ..., description: '')` | `Future<MyGroup>` | Makes an own group (#252) and returns it as the list shows it after the save: the group with the name and description sent that the list has after the save and did not have before (Smartschool's answer does not name its ID). Reads the list, loads the form for a new group for its token, and saves it once (see [Writes](#writes)). |
| `update(group, name: ..., description: ...)` | `Future<MyGroup>` | Changes the name, the description or both of an own group (#252), and returns it as the list shows it after the save. A `null` name or description keeps the one the group has, as its edit form has it (exactly: the list may not, see below); an empty description empties it. Reads the list (the group must be in it), loads the group's edit form for its token and values, and saves it once. |
| `delete(group)` | `Future<void>` | Deletes an own group (#252), with its member list. Reads the list (the group must be in it) and sends the delete once; it went through when Smartschool answers with the list without the group and the feedback "De actie werd correct uitgevoerd.". |
| `addMembers(group, users)` | `Future<bool>` | Adds people (`MessageSearchUser`s, as `MessagesService.searchRecipientsForCompose` finds them, of the own school) to an own group (#253): sends the current members and the new ones as the member picker's new selection, and posts the members form (see [Members](#members)). `true` once the members page Smartschool answers lists exactly those members; `false`, without sending a change, when each of them is a member already. The same person twice is added once. |
| `setMembers(group, users)` | `Future<bool>` | Makes those people the only members of an own group (#253), in place of its current members, in the same steps. `false` when they are its members already. An empty list is an `ArgumentError`: `clearMembers` empties a group. |
| `clearMembers(group)` | `Future<bool>` | Removes every member of an own group (#253), with an empty selection. `false` when it has none. |
| `removeMember(group, member)` | `Future<bool>` | Removes one member (a `MyGroupMember` of `members`) from an own group (#253): `POST /Profile/Mygroups/deleteUser`. `true` once Smartschool answered `true` and the members page after it no longer lists the member; `false`, without sending the removal, when the members page does not list the member. |

### What Smartschool answers

Seen live on 2026-11-16:

- **The list** is an HTML table with a row per group: its name, its description, and the links to edit it, to add people to it (`function=users&mID={id}`) and to delete it, which carry its ID. It does **not escape** a name or a description: a group named `a & "b"` is in the page as `a & "b"`, which the service reads as it is. A name that holds the text of an HTML entity (such as `&amp;`) is read as the character it names; only the group's edit form has such a name exactly. Smartschool strips tags when it saves a name or a description, so neither holds markup.
- **The members page** of a group has a row per member with the member's user ID and name, sorted by name, but not the member's platform (`ssId`), which a change of the members needs (#253). For an ID the user has no group of, Smartschool answers the list instead, with the feedback "De actie werd niet correct uitgevoerd!".
- **The member picker** ("Personen toevoegen" on the members page, Smartschool's general user picker) gives the platform. Loading the members page sets the picker's selection for the group (`usc` `mygroups_{id}`) in the PHP session to the current members, and the picker's dispatcher (`POST /?module=Userselect&file=dispatcher`, form-encoded `command`, the XML command format of the Messages dispatcher) answers the command `userSelect` / `get Items Selected` with that selection (`handle selected items`): each member as an `<item>` with its `type`, `id`, `ssId`, `name` and `schoolname`, or `<items />` for a group without members. The picker's own page did not need to be opened first. Without `X-Requested-With`, Smartschool answers the dispatcher with `302 Location: /?module=Homepage`; the service always sends it, and reports a redirect as a `SmartschoolMyGroupsError`.
- **The form** of a group (#252), `GET ...&function=addedit` for a new group and `...&function=addedit&mID={id}` for an existing one, is a `<form name="form" action="" method="post">` with a token (`_csrf_token`, a new one for every load), `store` (`1`) and the text inputs `name` and `desc`, filled in for an existing group (escaped in their `value`). It has no `mID` field: the ID is in the URL it posts to. For an ID the user has no group of, Smartschool answers the list with the feedback "De actie werd niet correct uitgevoerd!".
- **A save** (#252) posts the form, form-encoded, to the URL it was loaded from, with `_csrf_token`, `store`, `name` and `desc`, and is answered with `302 Location: /?module=Profile&file=mygroups&function=main` and an empty body, which does not name the group. Both fields go with every save. Text was saved as UTF-8 (`é` kept), with `&` and `"` as they are; tags are stripped (`gewijzigd <b>vet</b>` was saved as `gewijzigd vet`). The inputs have no `maxlength`; a limit of Smartschool was not tried.
- **A delete** (#252) is a GET, `...&function=delete&mID={id}`, which the web client sends behind a JavaScript `confirm()`. It is answered with `200` and the list itself (no redirect), without the group. A group with a member was deleted with its member list; the compose search of Messages no longer found it afterwards.
- **A change of the members** (#253) takes three steps in one PHP session. (1) `GET` of the members page: loading it sets the picker's selection of the group to its current members, and it holds a `<form name="form" action="" method="post">` with a token (`_csrf_token`), `store` (`1`) and an empty `mID`. (2) The picker's command `userSelect` / `confirm Selection`, with the `usc` `mygroups_{id}` and, as `xml`, the **whole** new selection, `<items><item><type>U</type><ssId>{platform}</ssId><id>{userId}</id></item>...</items>`; it answers `closeUsc` with the form name `form` (on which the picker's popup submits that form of the members page), and saves nothing: the members page read right after it still has the old members. (3) A `POST` of the members form, form-encoded, to the members page's URL, with `_csrf_token`, `store` and `mID`: it saves the selection and is answered with `200` and the members page, with the new members (and a new token). The selection **replaces** the members: `<items></items>` left a group without members. A `GET` of the members page between step 2 and step 3 resets the selection to the current members, and step 3 then saves those.
- **The removal of one member** (#253), the cross on a member's row, is `POST /Profile/Mygroups/deleteUser`, form-encoded `userID` and `groupID`, with `X-Requested-With` and without a token. It is answered with `200`, `application/json`, `true`, also for someone who is not a member (any more): the answer does not say whether anyone was removed.
- **The outcome** of a write is only in a feedback message in the next page Smartschool renders, in a script: `var msg = "...", type = N`. A save that Smartschool refused (an empty name: nothing changed) has "De actie werd niet correct uitgevoerd!" (type `2`) in the list after the redirect; one that went through has no message. A delete that went through has "De actie werd correct uitgevoerd." (type `1`); a delete, or the edit form, of an ID that does not exist (any more) "De actie werd niet correct uitgevoerd!" (type `2`). Smartschool keeps the message in the session until a page shows it.

The picker's request carries state of the session of the members page, so it is not retried after logging in again, nor sent in another session than the page's: when Smartschool refuses its session, or the client logged in again since the page was loaded, `members` loads the page again (logging in first) and asks the picker once more, and throws a `SmartschoolSessionExpiredError` when that fails too.

A change of the members (the picker's steps, which replace the selection, #253) must not have a load of the group's members page between its steps on the same session. The calls of `members`, `create`, `update`, `delete`, `addMembers`, `setMembers`, `clearMembers` and `removeMember` on one `SmartschoolClient` take turns, also those through another `MyGroupsService` of it; so no read of the members page comes between the steps of a change, and a write's reads of the list before and after its save see no other write of the client in between. Clients that share one session (one cache folder) do not take turns, nor do the calls of `list`.

### Writes

`create`, `update` and `delete` (#252):

- **Checks before saving.** A blank name, or one that is empty once its tags are stripped, is an `ArgumentError`, before anything is sent: Smartschool refuses it without saying why. So is `update` without a name and a description. A name that another own group has already, as the list shows it, is an `ArgumentError` once the list was read (its message names that group by its ID): whether Smartschool allows two such groups was not tried, and they could not be told apart in the compose search. `update` and `delete` only change a group the list has: another is a `SmartschoolMyGroupNotFoundError`, before anything is saved or deleted.
- **Sent once.** A save is never sent again after logging in again (its token is in the session), nor in another session than its form's; when Smartschool refuses the session for it, it fails with a `SmartschoolSessionExpiredError`, and nothing was saved. The service sends a delete once too (like every GET, it goes out again after logging in when Smartschool refused the session for it, and did not handle it then).
- **Confirmed.** The service follows the redirect after a save at once, as Smartschool keeps the feedback in the session, and checks the list it shows: no feedback that the save was not done, and the new group (`create`) or the group (`update`) with the name and description sent, as the list shows them. A delete is confirmed by its answer: the list with the feedback type `1`, without the group; with the feedback type `2` and without the group, it was gone already (a `SmartschoolMyGroupNotFoundError`). Anything else is a `SmartschoolMyGroupSaveUnconfirmedError`: **list the groups before trying again**, since a create that went through and is sent again makes a second group (which `create` refuses by its name).
- **Plain text.** Name and description are saved as plain text: Smartschool strips tags. The writes return the group as the list shows it after the save, without them.

### Members

`addMembers`, `setMembers`, `clearMembers` and `removeMember` (#253):

- **People of the own school.** `addMembers` and `setMembers` take `MessageSearchUser`s as `MessagesService.searchRecipientsForCompose` finds them (the `userId` and `ssId` that the picker takes; for the developer's own account they were the same as the picker's), or the own account (`MessagesService.getCurrentUserAsRecipient`). Each must have `otherSchool` `false`: a person of another school of the school group (`otherSchool` `true`, #238) was not tried, and is an `ArgumentError`, as is a person whose school is not known (`otherSchool` `null`, such as a recipient of a reply form), one without a user ID or platform, people of different platforms, and no people at all. Nothing is sent then.
- **Only people.** A group with a member that is not a person (a class or a Smartschool group, which the picker's tabs offer) is a `SmartschoolMyGroupsError` before any change is sent: what such a group holds was not tried. So is a member with the user ID of a person to add on another platform: the members page names members by user ID alone. `removeMember` of a member that is not a person is an `ArgumentError`.
- **One session, sent once.** `addMembers`, `setMembers` and `clearMembers` load the members page and read the picker's selection (as `members` does, so each current member comes with its platform), and send the new selection and the members form in the session of that page, **once** each: never again after logging in, nor in another session (the token and the selection live in it). When Smartschool refuses the session for one of them, it is a `SmartschoolSessionExpiredError`, and nothing was saved. A picker answer to the new selection that does not close on the members form is a `SmartschoolMyGroupsError`: the members form is not posted then.
- **Confirmed.** The change is confirmed when the members page that Smartschool answers the members form with lists exactly the members sent. The removal of a member is confirmed when Smartschool answered it with `true` and the members page read after it no longer lists the member (the `true` alone says nothing). Anything else after the form or the removal went out, a dropped connection included, is a `SmartschoolMyGroupSaveUnconfirmedError`: **read the members before trying again**. Sending the same change again changes nothing more.
- **Nothing to change.** Each returns `false` when there is nothing to change (the people are members already, the group has those members or none, the member is not in the group), after the reads, without sending a change.

The service posts the members form with `X-Requested-With`, as every form POST of the client; the live research posted it without (the live test of `test/live/my_group_members_write_live_test.dart` checks the answer).

The models never print a name: `MyGroup.toString()` names a group by its ID, `MyGroupMember.toString()` a member by its type, ID and platform. The members of a group are mostly pupils.

Not covered: the length of a name and two groups with one name (not tried), whether a pupil account has "Mijn groepen" (not tried), adding a class or a Smartschool group from the picker's tabs (whether the group then holds the class as one member or its pupils one by one: not tried), adding people of another school of the school group (not tried), and whether people are told that they were added to someone's group (nothing was seen for the own account).

### Errors

| Exception | Thrown when |
|---|---|
| `ArgumentError` | `create`, `update`: a blank name (or one that is empty without its tags), or a name that another own group has (once the list was read); `update` without a name and a description. `addMembers`, `setMembers`: no people, a person of another school or one whose school is not known, one without a user ID or platform, people of different platforms; `removeMember`: a member that is not a person (#253). Nothing was saved |
| `SmartschoolMyGroupsError` | Smartschool answered a read with something the service cannot use: another status than `200` (in `statusCode`; a redirect of the picker's request too), another page than the list, the members page or the form, a form without its token, a picker answer that is not `ok` or holds no selection, a row or item without its ID, or a members page and a picker selection that do not list the same members. Never an empty result; its message names a group by its ID only. From a write: a read before its save, so nothing was changed; from a change of the members (#253) also a members page without its form, a picker answer to the new selection that does not close on the members form (a redirect or another status included), a group with a member that is not a person, or a member with the user ID of a person to add on another platform: the members form was not posted. Not a session problem |
| `SmartschoolMyGroupNotFoundError` | `members`, `update`, `delete`, `addMembers`, `setMembers`, `clearMembers`, `removeMember`: the user has no own group with that ID (carries the `groupId`); for the writes, nothing was saved or deleted. A `SmartschoolMyGroupsError` |
| `SmartschoolMyGroupSaveUnconfirmedError` | `create`, `update`, `delete`: the save or the delete went out, but Smartschool's answer does not confirm it (carries the `groupId`, `null` for a create; the `statusCode` of an answer with another status than expected; the `cause` when no usable answer came in). `addMembers`, `setMembers`, `clearMembers`: the members form went out, but the members page answered does not list exactly the members sent, or cannot be read; `removeMember`: the removal went out, but was not answered with `true`, or the members page after it still lists the member or cannot be read (#253). The change may or may not have been made: list the groups (read the members) before trying again. Not a `SmartschoolMyGroupsError` |

The picker answering with an HTML page is a `SmartschoolUnexpectedPageError`, another answer that is not XML a `SmartschoolParsingError`, as for every XML command. A session Smartschool does not accept, also after logging in again, is a `SmartschoolSessionExpiredError`; no connection a `SmartschoolConnectionError`.
